# Break it

Try to break your own work on exactly what the request promises. Never skip it because the demo passes. On the standard route `herd done` and the Stop gate refuse until each of the six standard attacks below has a command that `herd verify` ran and saw pass.

The attacks shape the design. Before the first `herd verify`, and so before any code, read this file, decide what each attack means for your input, and log all six, each with its command (or `--covered-by`) or `n/a:`. They should fail then.

1. Turn each quantifier or size word in the request (`any`, `every`, `whatever`, `many`, `big`, `very big`) into hostile inputs:
   - generated cases from several different shapes or families, and purely random ones you did not design;
   - size and shape extremes: huge, degenerate, disconnected;
   - a scale run with a time limit.
2. Always run the six standard attacks, whatever the request says. Write each as a command that fails if the attack breaks the work (usually a regression test), and log it before building: `herd note --tried --attack <name> --check "python3 -m unittest tests.test_errors" "what it covers"`. `herd verify` runs it like a criterion check; a failing command, one that runs zero tests, or one that runs no project code (`true`, `echo`, `test -f`) does not count.
   - `--attack bad-input`: bad input at every entry point (each file, argument and record a user supplies): missing, unreadable, malformed, wrong type, unknown id, empty. Each must end with one clear message and a non-zero exit, never a traceback.
   - `--attack collision`: two cases. Distinct entries that share a name, value or position (the same key): each one must still be counted. Input that contradicts itself (one identity given twice with different data): it must be refused, unless the request says which one wins. Decide what identifies an entry from the input's own identity fields.
   - `--attack one-bad-part`: skip a broken or unreachable entry that the request does not ask for only when skipping it cannot change a requested answer (any output the request asks for). If it could, or you cannot tell, fail with a clear message; a requested entry that is broken or unreachable always fails. A warning on stderr with exit 0 is never a refusal.
   - `--refuses "<cmd>"` is your program on input it must refuse: contradictory input for `collision`, a broken requested entry for `one-bad-part` (both needed at medium and high risk; optional for `bad-input`). `herd verify` runs it: it must exit 1 to 125, write to stderr and print no `Traceback`. For `collision` only, when no input can contradict itself or the request says which one wins, give `"n/a: <reason>"` as its value: the report shows it as not run.
   - `--attack recount`: recompute every reported number (totals, times, counts) from the output itself, such as the trace or the rows, with separate code, on the generated and collision inputs too. Never check a number with the code that produced it.
   - `--attack refusal`: every kind of input the program refuses (cannot be reached, not found, invalid) is a claim too. On generated inputs, confirm each refusal with separate, simpler code (such as a plain search), and check that nothing the program could serve is refused. List what the program will refuse before building. Never decide a refusal with the code that made it.
   - `--attack other-reading`: a person who never saw your program can read each `[[inputs]]` entry in more than one way (a date as `03/04/2026` or `2026-04-03`; a table with or without a header row). For each entry, name at least two readings of the human's words in the note, and generate inputs in each one with code that calls no project code (the readings listed for the entry in task.toml: generate in every one). The program must serve every reading itself: it never refuses one, and the caller never chooses, converts or pre-computes anything. `n/a:` only when the task has no inputs. At every risk add `--example "<cmd>"`, your program on the input written as the human described it, with `--expect "<text>"`. Solve a tiny case by hand and write its answer as the text, before any code; never paste the program's own output. `herd verify` runs the command: it must exit 0, print to stdout, and stdout must contain the text exactly (a plain substring, ends trimmed). The text is frozen at the first `herd verify`: a different or late one needs `--expect-changed "<reason>"`, which the report lists. Change it only when your hand answer was wrong.
   For `recount`, `refusal` and `other-reading` only: when a criterion's check already does the attack's job, write no second test. Log `--covered-by <criterion id>` in place of `--check`: `herd note --tried --attack recount --covered-by C3 "what it covers"`. The attack passes exactly when that check passed in the latest `herd verify`; one that ran zero tests or no project code does not count. Herd does not check that the test meets the attack's rule above: that is yours to judge. `other-reading` still needs its example command and expected text (above).
   An existing test, such as a criterion's check, counts for an attack only if it meets that attack's rule above: every entry point for bad-input, separate code for recount. Give that test as the `--check` and say what it covers. An attack that cannot apply has no command and text starting `n/a:` with the reason: `herd note --tried --attack collision "n/a: the tool takes one value"`. The report shows it as n/a.
3. Run them. If you can spawn a fresh-context subagent, give it only the request, the criteria and how to run the tool, and ask it to break it. Otherwise do it yourself and say it was not fresh.
4. Log each attempt with `herd note --tried` (plus `--attack <name> --check "<command>"` for a standard attack; a later note for the same attack replaces a wrong command), each failure with `--found`, each fix with `--fixed`, each limit you leave with `--open`, as the run skill's Rules say.
5. Turn each failure into a regression test, then fix it.
6. A known limit that narrows a human any/every claim (only, first, rejected, skipped, assumed) is shown to the human as not proven. Prefer testing the claim under it, or lifting it.
